# Atlas Hardware Continuity — Governing Premise

Status: **Premise v0.1**  
Date: **2026-09-04**

Atlas should be built so that dedicated Atlas hardware, if and when it comes, is not a separate product inspired by the software.

It should be **the same Atlas continuing into a physical form**.

## The premise

The long-term device is not a better smartphone and should not be designed around recreating the current catalog of phone applications.

It is a trusted physical endpoint of a person's or institution's Atlas.

The person, household, institutions, relationships, authority, communication, obligations, projects, money, inventory, knowledge, and history already exist in Atlas. A handheld device, tablet, laptop, household node, or future hardware surface is a place through which that existing world can be perceived and acted within.

The hardware does not define Atlas. Atlas gives the hardware meaning.

## Simple living above complex infrastructure

The last several decades of personal computing have required people to manage an increasing number of artificial boundaries: apps, accounts, inboxes, tabs, websites, passwords, integrations, notifications, file systems, provider identities, duplicated records, and repeated data entry.

Atlas is not trying to reproduce all of those boundaries more elegantly.

Its direction is to absorb as much of that machinery as possible beneath a coherent representation of actual life and institutional reality.

A person should be able to communicate, work, care for a household, run a business, receive information, make decisions, create, pay, sell, schedule, delegate, and retrieve knowledge without continually managing the historical accidents of the software industry.

The desired human experience is simpler because Atlas carries more of the digital complexity correctly—not because reality itself is hidden or reduced.

## Commodity infrastructure beneath Atlas

Atlas hardware does not require Atlas to own every physical network or recreate every external service.

Commodity internet connectivity, cellular networks, existing computers, web resources, carriers, and external protocols may remain useful infrastructure underneath or outside Atlas.

Their presence should not define the user's conceptual world.

If Apple, Google, carriers, cloud vendors, messaging systems, browsers, or application conventions change, Atlas should absorb those changes at its boundaries wherever possible rather than repeatedly forcing users to reorganize their lives around them.

## Family and institutional devices

The future device model must be able to begin from real human relationships rather than consumer-account assumptions.

A teenager's Atlas device can be understood first as a device held by a particular child within a particular household under real family authority. A worker's device can be understood in relation to the institution and capacity in which it is used. A shared household or institutional device need not pretend to be one permanent human identity.

This is not primarily a parental-control feature or enterprise-device-management feature. It follows from correctly modeling person, household, institution, device, capacity, and authority as distinct realities.

## Continuity requirement

Present software decisions must therefore avoid making the future hardware team recreate Atlas around assumptions that only happen to be true of today's web application.

In particular, Atlas must not depend conceptually on:

- person = authentication account;
- device = person;
- phone number or email = identity;
- cloud = only possible custodian;
- browser = permanent primary interface;
- current route/screen hierarchy = Atlas itself;
- external messaging provider = communication system;
- current application boundaries = permanent boundaries of human activity.

We do not yet know the processor, operating system, radio, display, enclosure, manufacturing partner, or exact capabilities of future Atlas hardware.

We do not need to know them yet.

What matters now is that the Atlas built in software can continue into that hardware without changing what Atlas is.

The future object in the user's hand should not be a new product that imports Atlas.

It should be **another place Atlas exists**.
